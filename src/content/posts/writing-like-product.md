我写过最难读的文档,是自己三个月前写的《xxx 接入说明》。

当时觉得写得挺全,现在只剩一个感受:找不到重点。

后来发现这不是能力问题,是**结构问题**。技术写作和写代码一样,先定结构,再填内容。

## 三层结构

任何一篇技术文档,读者的耐心只有三层:

1. **结论**:一句话告诉我该不该继续读;
2. **条件**:什么情况下适用,什么情况下不适用;
3. **细节**:怎么做、为什么这么做。

绝大多数文档失败在第一层 —— 开头是三段背景介绍,读者翻了两屏还不知道你想说什么。

对比一下:

```text
✗ 随着业务发展,系统的图表数量越来越多,性能问题逐渐显现。
  本文将从多个角度分析……(以下 400 字铺垫)

✓ 大屏图表超过 8 个时,ECharts 实例会成为主要瓶颈。
  本文给出三个可控方案,并说明各自的代价。
```

第二版把"结论"提到了第一句。

## 小标题要能被扫读

判断方法:**只读所有小标题,能不能猜出全文结构。**

```text
✗ 关于性能的一些思考
✓ 瓶颈在实例数,不在数据量
```

小标题里应该出现**名词和判断**,而不是"简介"、"说明"、"总结"。

## 代码块要给上下文

只贴代码是最常见的偷懒。一段独立可读的代码需要三个东西:

- **它在哪**:哪个文件、哪个函数里;
- **它为什么**:解决什么问题;
- **它有什么坑**:复用时要注意什么。

```ts
// 销毁时要连贴图一起释放, 否则显存泄漏
function disposeNode(node: THREE.Object3D) {
  // ...
}
```

那一行注释的价值,往往大于整段代码。

## 表格 vs 列表 vs 图

- **对比**用表格(两三个维度);
- **步骤**用有序列表(有先后);
- **并列条件**用无序列表(无先后);
- **趋势/结构**才值得画图。

我见过用流程图描述三步操作,也见过用 12 条列表罗列对比数据。都是错配。

## 写完之后做一次检查

我用一张固定的清单:

| 检查项 | 问题 |
| --- | --- |
| 第一段有结论吗 | 没有就重写 |
| 小标题能扫读吗 | 只读标题能不能看懂 |
| 每个代码块有上下文吗 | 贴完有没有解释 |
| 有"为什么"吗 | 只有"怎么做"的文档活不过半年 |
| 长度能砍掉 20% 吗 | 基本都能 |

最后一项的命中率是 100%。**删掉所有"值得一提的是"、"众所周知"、"毋庸置疑"。**

## 一个副作用

开始这样写之后,我发现代码也被影响了:函数开头先写"这个函数解决什么问题",复杂分支写"为什么不是另一种写法"。

写清楚是思考的一部分,不是思考之后的整理工作。
